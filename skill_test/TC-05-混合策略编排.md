## 执行过程

### Phase 1: 001（explore）

当前 session 通过 `read_only_task()` 派发：

```
STATUS: COMPLETE
STEPS:
  Step 1: grep 项目是否有 prometheus / metrics → 无
  Step 2: grep requirements / pyproject → 无 prometheus_client 依赖
  Step 3: 结论 → 项目尚无监控设施，需新建
NOTES: 建议使用 prometheus_client + /metrics 端点
```

### Phase 2: 002 + 003 串行（依赖 001 完成）

001 完成后，002 和 003 可以**并行**（它们都只依赖 001，互不依赖）。

但是 002 和 003 的标记是 `direct`，意味着当前 session 串行执行。

这里有一个优化空间：如果两个子任务不互相依赖且都是 direct，是否可以提升为 parallel？

**规则修正：** 同依赖级别的 direct 子任务，如果不互相依赖，允许 parallel 执行。

所以 002 和 003 用 `task()` 并行派发：

```
task-002: 添加 metrics 埋点 → COMPLETE
task-003: 暴露 /metrics 端点 → COMPLETE
```

### Phase 3: 004 + 005 并行（依赖 002+003 完成）

004 和 005 原本就是 parallel 标记，直接用 `task()` 并行派发：

```
task-004: 编写 Grafana 看板 → COMPLETE
task-005: 测试 metrics 采集 → COMPLETE
```

每种格式分别报告：

```
STATUS: COMPLETE
STEPS:
  Step 1: done → pytest test_metrics.py 全部通过
FILES CHANGED: src/bugvault/metrics.py, tests/test_metrics.py
```

## Review 汇总

对所有 5 个子任务分别做 §5 Review。

002 的 Review 发现一个问题：

| Before | After | 说明 |
|--------|-------|------|
| `async def call_tool(...)` | 添加了 `metrics_collector.record()` | 打点 |

问题：`prometheus_client` 的 `start_http_server` 是同步阻塞调用，在异步 MCP server 中会阻塞事件循环。

**Verdict: BLOCK（002）**

原因：spec 未考虑异步环境下的 metrics 暴露方案。
行为：回到 §3 重写 002 的 spec，改用 `aiohttp` + `prometheus_async` 或异步兼容方案。
