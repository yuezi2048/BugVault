## 二、关键认知（横向对比）

### 2.1 BugVault vs AgentMemory

| 维度 | BugVault | AgentMemory |
|------|----------|-------------|
| 定位 | 垂直排障引擎 | 通用记忆平台 |
| 核心差异 | `tried_methods` 强制失败复盘 | 通用观察→压缩→记忆 |
| 工作流 | preflight + postflight 编排 | 无 |
| 检索深度 | ANN + BM25 + RRF + Cross-Encoder + 时间衰减 | BM25 + Vector 线性加权 |
| 生态 | 5 个 MCP tool, 0 star | 128 endpoints, 15 skills, 25.1k⭐ |

**核心结论**：BugVault 的差异化在于 **工程纪律**（不是存更多，而是强制复盘失败路径），而非功能数量。AgentMemory 放权给 LLM，BugVault 用系统约束 LLM。

### 2.2 BugVault vs DeepMiner

- DeepMiner 是学术论文框架（**无开源工程**），优化单会话内长上下文（滑动窗口 100轮/32k）
- BugVault 管跨会话记忆，DeepMiner 管会话内上下文，两者**互补而非竞争**

### 2.3 BugVault 不是玩具

- 178 个测试、15 份设计文档、Cross-Encoder 重排序、RRF 融合——质量超过 80% 个人项目
- 简历价值在于「工作流编排 + RAG 系统设计 + 工程纪律」三个叙事维度
- 建议定位：先以「Reasonix/Claude Code 智能工作流管家」身份发布，而非「AgentMemory 替代品」

## 八、后续迭代补充（2026-07-28）

> 本节记录 SESSION-001 之后的架构演进。其中 Retrieval 模块已提交；Record persistence 模块仍在当前工作区验证，尚未提交。

### 8.1 Retrieval 模块深化（已提交）

对应提交：`d62b482 refactor(retrieval): deepen local memory pipeline`

此前 MCP adapter 同时承担协议解析、候选召回、排序和文本格式化，导致检索逻辑难以在 benchmark 或其他入口复用。本次把检索主路径收敛到 `RetrievalModule`：

```
MCP / benchmark
      │  RetrievalRequest
      ▼
RetrievalModule
  ├─ chunk 向量召回
  ├─ chunk FTS 召回 + RRF 融合
  ├─ chunk → parent 完整记录映射
  ├─ 元数据和 record_type 过滤
  └─ 可选 Cross-Encoder 精排
      │  RetrievalResult
      ▼
MCP adapter（展示 / RAG judge 调用）
```

| 变化 | 目的 | 结果 |
|------|------|------|
| `RetrievalRequest` / `RetrievalResult` | 建立稳定的领域输入输出边界 | MCP 不再以文本响应作为检索模块的内部协议 |
| `RetrievalModule` | 收拢 chunk 召回、父记录还原、RRF 和精排 | benchmark、MCP 可共用同一条检索链路 |
| FTS 父表回退 | chunk 表无候选时保留兼容查询路径 | 旧数据或异常场景仍可返回关键词命中 |
| adapter 瘦身 | MCP 只负责传输和结果呈现 | 减少协议层与领域层耦合 |

当前检索仍有两个明确限制：`tech_stack` / `project_name` 使用字符串 `LIKE` 过滤（仅对 Java 与 JavaScript 做了歧义排除）；可选的 RAG judge 是远程能力，只有关闭它时才能保证查询全本地执行。

### 8.2 Record persistence 模块深化（工作区待提交）

新增 `RecordPersistence`，把一条 Bug Record 或 Convention Record 的完整落库生命周期收敛为一个领域模块：

```
MCP save tool
      │
      ▼
RecordPersistence.prepare_*
  ├─ 构建并校验领域记录
  ├─ 完整记录写 Markdown archive
  └─ 草稿返回缺失字段（不归档）
      │
      ▼
RecordPersistence.persist
  ├─ 一次批量 embedding：parent + chunks
  ├─ LanceDB upsert parent / chunks
  └─ LadybugDB Graph 节点与关系投影（非致命）
```

| 问题 | 本次处理 | 价值 |
|------|----------|------|
| MCP 保存路径职责过多 | MCP 仅组装参数、呈现保存结果、调度后台写入 | 领域逻辑可单测、可复用 |
| parent 与 chunks 分散生成向量 | 使用一次 `generate_embeddings()` 批处理 | 降低模型调用次数，保证写入边界一致 |
| archive rebuild 重复 embedding 逻辑 | 重建流程复用 `RecordPersistence.embed()` | 避免在线写入和离线恢复产生结构漂移 |
| Graph 初始化后未接入保存路径 | LanceDB 写入后投影 Bug / Convention 图关系 | 图数据开始与本地记忆保持同步 |

这里的 Graph 仍是**写侧投影**，并没有 graph-backed retrieval；不能把它描述成图检索已经上线。后台 embedding 任务也还不是持久化队列，若进程在任务完成前退出，尚未写入的本地记忆不会自动恢复或重试。
