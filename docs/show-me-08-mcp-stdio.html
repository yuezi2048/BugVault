参数校验的两层落点第一层不强制tools.py:41–195，persistence_svc.py:135–150

两层分工不同：第一层是给客户端/模型看的契约，第二层才是服务端真正的拦截点。

第一层MCP inputSchema（JSON Schema）
  • 随 tools/list 返回，告诉客户端参数名、类型与 required（tools.py:41,89,103,134,165；如 _RETRIEVE_SCHEMA.required=["query"] :86）。
  • enum 也是契约的一部分：eval_depth ∈ none/simple/claim_level（:51–60），error_category 5 个取值（:175–185）。
实况：仓库里只有 5 处 inputSchema= 赋值，没有任何 JSON Schema 校验调用；不满足 schema 的参数不会被服务端按 schema 拒绝。
第二层Pydantic 模型校验（硬 + 软）
  • 硬校验：BugRecord(**arguments) / ConventionRecord(**arguments)（persistence_svc.py:136）；字段长度约束在 bug_record.py:31–60、convention_record.py:36–60。
  • 软校验：missing_required_fields()（bug_record.py:108–114 只查 tried_methods / final_solution；convention_record.py:114–120 只查 incorrect_behavior / correct_behavior）→ 命中即 draft。
  • 失败落点：PreparedRecord(record=None, validation_error=str(exc))（persistence_svc.py:137–142）；draft 落点 missing_fields（:144–150）。
返回文案：非法 Invalid record: ... / Invalid convention: ...（tools.py:471–482）；draft saved as draft. Missing fields: ...（:484–493）。
落差（写入工单 Answer）
  • 第一层空转inputSchema 只对外暴露，服务端不校验；客户端传错参数时第一层不会拦截，实际由 Pydantic 拒绝，报错文案是 Python 校验信息而非 schema 违规说明。
  • 检索类不建模retrieve_bug_experience / retrieve_convention 不构造 Pydantic 模型，只做 arguments.get("query", "")（tools.py:527–530、594–595），空值由检索层兜底（retrieval_svc.py:68–71）。
  • 反思工具无模型reflect_and_prevent_error 走 _sync_reflect 手工判空（tools.py:792–800）；PreventionRule 模型已定义但全仓库无实例化引用（reflection_rule.py:8）。
错误返回契约：trace_id → ErrorCode → JSONL分类存在不可达分支tools.py:309–412，observability.py:126–235，error_code.py:12–31

每次 tools/call 进入时生成 trace_id，退出时按 ErrorCode 分类写一行 JSONL；同一 trace_id 也进入该请求的所有日志行。

1生成 trace_id：set_trace_id() 取 uuid4().hex[:12] 写入 contextvar（logger.py:32–40），TraceIdFilter 把它注入每条日志（logger.py:50–57）。
2分类：成功路径硬编码 status="ok", error_code="ok"（tools.py:379–384）；异常路径 _classify_error(exc) 按关键词匹配（observability.py:217–235）。
3落盘：AiCallLogEntry(event_type="entry"|"exit", ...)（observability.py:77–118）经 append_ai_call_log 追加到 {data_root}/log/ai_call.jsonl（:126–139），默认 ~/.bugvault/log/ai_call.jsonl（config.py:19）；entry 会剔除 eval_llm_api_key（tools.py:319）。
ErrorCode（error_code.py:16–31）分类触发是否可达
ok成功返回，硬编码字符串（tools.py:381）可达
rate_limited / timeout / auth_fail / content_safety / parse_error / internal异常消息关键词：rate limit、timeout、auth、content+safety、parse/json/decode，兜底 internal（observability.py:224–235）可达
validation_error枚举已定义（error_code.py:26），但 _classify_error 从不返回它；校验失败走正常 return不可达
not_found枚举已定义（:30）；空结果也是正常 return，日志记 ok不可达
quota_exceeded枚举已定义（:31）；claim_level 配额耗尽在评测层降级为 simple (fallback_from_error)（rag_evaluator_svc.py:593–615），不走该码不可达
落差（写入工单 Answer）
  • 失败记成功非法参数与空检索结果都经正常 return 收尾，exit 日志写 status="ok", error_code="ok"（tools.py:376–390），JSONL 里看不出这次调用实际没交付内容。
  • 异常包成文本异常被包成 Error executing {name}: {exc} 的 TextContent 返回（tools.py:409–412），不抛 JSON-RPC error 对象；是否标记 isError 由 mcp SDK 决定，仓库未显式设置。
  • trace 不回传trace_id 只进服务端日志与 JSONL（tools.py:310,322；observability.py:103），结果文本里没有，客户端无法凭返回内容关联到服务端日志。
  • 子串误判auth / content 等判定是子串匹配（observability.py:228–231），普通报错里出现这些词会被误分类。
客户端接入：一份 mcpServers 片段，处处运行README.md:155–171,462–477README.md:158–171，462–477

客户端只需要知道「怎么启动这个子进程」；工具集、参数与说明都在 tools/list 里自描述（tools.py:236）。所以同一段配置（仅 --directory 路径不同）可直接粘进任一支持 MCP stdio 的客户端，不需要为 BugVault 写适配代码。

写法 A：命令行里有 uv（README.md:158–171）

{
  "mcpServers": {
    "bugvault": {
      "command": "uv",
      "args": [
        "run",
        "--directory", "/path/to/bugvault",
        "python", "-m", "bugvault.main"
      ]
    }
  }
}

写法 B：绝对路径更稳（README.md:462–475）

{
  "mcpServers": {
    "bugvault": {
      "command": "/path/to/uv",
      "args": [
        "run",
        "--directory", "/absolute/path/to/bugvault",
        "python", "-m", "bugvault.main"
      ]
    }
  }
}
